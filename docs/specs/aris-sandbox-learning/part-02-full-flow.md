## 4. 系統生命週期

### 4.1 發現改進機會

改進機會的來源：
- **Aris 自主發現**：AgencyLoop 執行過程中的觀察（測試失敗率、成本趨勢、gbrain 命中率、S_span 成績）
- **Ryan 直接指定**：Ryan 提出一個問題或需求，要求 Aris 分析
- **事故觸發**：回退事件、安全閘 DENY、watchdog 重啟觸發檢討
- **上游更新**：lorryjovens-hub/laap-AGI 有新 commit 時，評估是否需要同步

### 4.2 判斷是否真的有必要

在進沙箱前先回答：
1. 這個問題是否真實存在？（證據在哪裡？）
2. 這個問題是否已經被解決過？（搜尋既有案例）
3. 不做會有什麼後果？
4. 有沒有比進沙箱更小的解法？（改 config、env 變數、文件說明）

### 4.3 建立問題與改進假設

使用 Chapter 5 的格式建立正式的「問題與假設」文件。這份文件是整個流程的起點，也是後續所有判斷的錨點。

### 4.4 預測好處、壞處、風險、代價

Aris 必須在進沙箱前明確寫下預測。這是學習的關鍵：後續的「預測誤差」依賴於此時的預測。

預測格式（簡化版，詳見 Chapter 10）：
- **好處**：預期改善什麼？改善多少？誰感受得到？
- **壞處**：新增什麼複雜度、依賴或限制？
- **風險**：最壞情況是什麼？發生機率？可回退嗎？
- **代價**：開發時間、API 成本、Ryan 注意力成本

### 4.5 決定是否進入沙箱

判斷條件（詳見 Chapter 8）：
- ✅ 問題有客觀證據
- ✅ 沒有更小的解法
- ✅ 預期好處值得代價
- ✅ 能建立客觀驗收條件
- ✅ 能完整回退
- ❌ 涉及正式資料（不可進沙箱）
- ❌ 涉及不可逆外部副作用（不可進沙箱）
- ⚠️ 只能觀察、不實作（當證據不足時）

### 4.6 建立一次性 Git worktree

```bash
git worktree add --detach /tmp/aris-sandbox-001/ HEAD
```

- 沙箱分支命名：`sandbox/<編號>-<簡短描述>`（如 `sandbox/001-fix-s-span-bench`）
- Base commit = 目前 main 最新
- 沙箱目錄不可在正式工作區內
- 沙箱的 git config 隔離（不同 user.name/email，避免混淆）

### 4.7 Scream 實作候選方案

Scream 在沙箱 worktree 中：
1. 讀取現有程式碼
2. 做最小修改（只改解決問題需要的部分）
3. 每步修改都 commit（沙箱內 commit，不影響 main）
4. 對應於問題與假設中的成功/失敗條件

### 4.8 執行測試與驗證

測試流程：
1. 跑既有測試（確認沙箱修改沒有破壞既有功能）
2. 跑針對修改的新測試（確認修改確實解決了問題）
3. 跑 benchmark（如果有）
4. 記錄所有測試輸出（stdout + exit code + 執行時間）

### 4.9 產出候選變更包

使用 Chapter 9 的格式產生完整的候選變更包，包含：
- diff、測試結果、行為前後差異、已知風險、回退方法
- 這是 Ryan 決策的主要參考文件

### 4.10 Aris 提供決策分析

使用 Chapter 10 的格式做四面向分析。Aris 必須誠實標註信心強度，不可為了讓方案通過而誇大信心。

### 4.11 必要時交給外部 AI 參謀

觸發條件（詳見 Chapter 13）：
- Aris 信心低於門檻（如 < 0.6）
- 高風險或高影響
- 涉及核心架構或安全邊界
- 測試結果矛盾
- Aris 與 Scream 判斷不同

### 4.12 Ryan 選擇落地、修改、觀察或回退

Ryan 的選項（詳見 Chapter 12）：
1. **直接落地**：批准候選方案
2. **縮小範圍**：只取方案的一部分落地
3. **沙箱繼續觀察**：不批准也不拒絕，等更多證據
4. **退回修改**：要求 Scream 修改後再送審
5. **完全回退**：拒絕方案，關閉沙箱
6. **採用替代方案**：Ryan 提出另一個解法
7. **暫時不做**：延後處理
8. **蒐集更多證據**：要求 Aris 補資料

### 4.13 落地後持續追蹤

落地後：
- 立即健康檢查（Aris status、S_span benchmark、healtcheck API）
- 7 天跟蹤：修改是否有預期效果？有沒有副作用？
- 30 天跟蹤：長期效果？維護負擔？

### 4.14 比較預測與真實結果

關鍵學習步驟：
- 好處：預測 vs 實際（改善幅度、使用者感受）
- 壞處：預測 vs 實際（新增複雜度、維護負擔）
- 風險：預測 vs 實際（事故發生率、嚴重程度）
- 代價：預測 vs 實際（時間、成本、注意力）

### 4.15 形成新的學習案例

使用 Chapter 18 的格式記錄完整的學習案例。這是自主學習的「原子單位」。

### 4.16 更新候選判斷策略

當累積足夠案例後，學習引擎可產出候選策略校準。策略升級需經過：
1. 歷史回測（用既有案例驗證新策略是否更好）
2. Held-out 驗證（用未參與訓練的案例驗證）
3. Shadow mode（新策略只輸出建議，不取代舊策略）
4. Ryan 批准

### 完整流程圖

```text
問題
→ 預測
→ 沙箱實驗
→ 客觀證據
→ Aris 分析
→ 外部 AI 第二意見（條件觸發）
→ Ryan 決策
→ 真實結果
→ 預測誤差
→ 策略學習
→ Shadow 驗證
→ 人類批准策略升級
```

## 5. 問題與假設格式

每個改進機會必須用以下格式記錄。這是最小可行格式，若有多個問題應分開記錄。

### 5.1 問題是什麼

一句話描述：

> 範例：`S_span bench 的 timeout 機制是無限等待，導致 benchmark 卡住時永遠不會結束`

### 5.2 問題是否真實存在

客觀證據（不可是「我覺得」或「可能」）：
- [ ] 有 log 記錄
- [ ] 有 test 輸出
- [ ] 有人親眼看到（Ryan 回報）
- [ ] 有數值趨勢

> 範例：`2026-07-18 手動執行 extended S_span bench，執行 347s 未結束，手動 kill。log 無 timeout 訊息。`

### 5.3 目前證據

相關資料連結或附錄：
- 錯誤 log 路徑
- 測試輸出
- benchmark 數據
- 相關程式碼檔案和行數

### 5.4 預期改善

客觀可量測的改善標準：

> 範例：`max 60s timeout，超過則記錄 timeout 並優雅退出，不影響其他測試`

### 5.5 可否被證偽

一定要能證明「這個方案沒用」或「問題已解決」：

> 範例：`可證偽：如果加 timeout 後 benchmark 仍然卡住超過 60s 不退出，則方案無效`

### 5.6 最小實驗

解決此問題的最小程式修改描述：

> 範例：`在 s_span_bench.py 的每個測試循環加 timeout=60 參數`

### 5.7 成功條件

可客觀驗證的成功定義：

> 範例：`timeout 後 benchmark 記錄 timeout 事件並優雅退出，exit code 0`

### 5.8 失敗條件

可客觀驗證的失敗定義：

> 範例：`timeout 後 benchmark crash／hang／exit code 非 0`

### 5.9 停止條件

何時該終止此沙箱實驗：

> 範例：`若實作後 3 次測試中有 2 次仍發生無限等待，則停止`

### 5.10 不做會怎樣

如果不處理此問題的後果：

> 範例：`extended benchmark 不能自動化跑，需人盯`
